# Format authoring readiness

> Historical planning and upstream audit. Some proposals and pinned-source references are superseded; use the [operation support matrix](support-matrix.md) and [authoring guide](authoring.md) for current behavior. For the current PPTX render-panic contract, see [rendering](formats.md#rendering).

Historical source audit: 2026-10-20. Subsequent implementations are recorded in [the authoring guide](authoring.md), [format support](formats.md) and the [validation ledger](../.kiro/specs/rust-document-engine/validation.md). The sequencing below records the initial plan, not current release status. This records implementation entry points for [W06](https://github.com/narain1/pydoccraft/issues/8), [W10](https://github.com/narain1/pydoccraft/issues/12), and [W11](https://github.com/narain1/pydoccraft/issues/13). It does not mark their authoring features implemented. The common editable lifecycle and preservation baseline in [W03](https://github.com/narain1/pydoccraft/issues/5) comes first; W06 also needs the W04 text/style baseline. Follow the [compact API design](authoring-api-design.md) and [upstream register](upstream-roadmap.md).

All symbols below were inspected at the repository's pinned revisions. Availability of a public model or writer establishes an integration route, not complete rendering fidelity or safe arbitrary-file round trips.

The first W10 slice should create a blank native PDF and add bounded images, then serialize, reopen, and render. Page organization follows with a separate dependency audit. Preserve documented behavior: deletion refuses to remove every page, and `replace_pages` replaces visible page content while retaining target links/comments/widgets. Failure atomicity and cross-document resource handling need corpus tests. [Organization implementation](https://github.com/storytold/pdfcraft/blob/645016addcfb9078c557f0189559ab47cdcee057/crates/organize/src/lib.rs#L195)

Annotations, AcroForms, and verified redaction remain separate acceptance slices within W10, not implied by basic drawing. U10 should capture specific public API or correctness gaps discovered by those tests; existing creation/organization APIs are not upstream blockers.

## W11: PPTX authoring and preservation

`deckcraft_pptx::export` already writes PPTX, and `export_as` supports template/show package variants. `import_theme` returns a theme plus media. The package documents lenient import, so a successful read/write alone cannot prove complete preservation. [PPTX entry points](https://github.com/storytold/deckcraft/blob/22db9261f9d1a214c296fd390173130c45d76d66/crates/pptx/src/lib.rs#L1)

`Presentation::default`, `slide_mut`, `alloc_id`, and `add_media` provide model construction and mutation. Slides, masters, layouts, backgrounds, notes, and shape kinds are public. Reuse the common lifecycle, ordinary collections, and shared text/image/table concepts; do not expose a separate command/session layer. `alloc_id` and `add_media` may fail and must not produce duplicate IDs. [Presentation API](https://github.com/storytold/deckcraft/blob/22db9261f9d1a214c296fd390173130c45d76d66/crates/model/src/lib.rs#L967)

The first W11 slice should construct a basic presentation, edit one slide's text/background, export, reopen, and render it. Next add image placement with media deduplication and bounded shape groups. `Presentation::validate` checks selected ID/layout relationships; supplement it with operation-specific validation rather than treating it as a complete package validator. `ShapeKind::Opaque`, `raw_ext`, and `kept_parts` provide preservation mechanisms, but arbitrary unsupported parts need fixture evidence. U11 covers deeper reference/preservation guarantees, not a missing writer. [Opaque shapes](https://github.com/storytold/deckcraft/blob/22db9261f9d1a214c296fd390173130c45d76d66/crates/model/src/lib.rs#L286)

PDF export renders slide artwork and adds searchable text; it is not a general vector-preserving export. Selected slide indexes are filtered upstream, so a future Python selection option must reject invalid indexes first. [PDF implementation](https://github.com/storytold/deckcraft/blob/22db9261f9d1a214c296fd390173130c45d76d66/crates/pdf/src/lib.rs#L130)

## W02 rendering slice and remaining constraint

The local rendering change adds PDF/DOCX PNG resolution metadata, complete RGBA validation, and DOCX/PPTX size checks before raster allocation. Requested DPI is finite and within 1–1200. Every raster is limited to 64,000,000 pixels (256 MB of RGBA, excluding working allocations); PDF also has an 8,192-pixel side cap, DOCX/PPTX a 16,000-pixel side cap. Requests exceeding limits fail rather than returning a silently resized image. PDF already applies the matching pixel cap with `reject_oversize`; Office requests now get a conservative ceiling-based preflight. [PDF limits](https://github.com/storytold/pdfcraft/blob/645016addcfb9078c557f0189559ab47cdcee057/crates/render/src/raster.rs#L130)

Pixel rounding remains engine-specific: PDF rounds upward with a small float-noise tolerance, DOCX rounds upward, and PPTX rounds to nearest. PNG physical resolution is encoded in integer pixels per meter, so its recovered DPI has quantization error up to approximately 0.013. Tests cover 72, 144, 150.5, and 300 DPI, visible fixture content, aliases/indexes, invalid inputs, oversized requests, and a valid blank page. Build/installed-wheel results belong in the [validation record](../.kiro/specs/rust-document-engine/validation.md).

Historical U09 finding: DeckCraft catches rendering panics and returns a correctly sized blank image, which dimensions alone cannot identify. The current adapter checks a process-wide panic counter and returns an error when it changes. This can produce a spurious error when another thread panics; a fallible per-call upstream result remains preferable. [DeckCraft render fallback](https://github.com/storytold/deckcraft/blob/22db9261f9d1a214c296fd390173130c45d76d66/crates/render/src/lib.rs#L388)
